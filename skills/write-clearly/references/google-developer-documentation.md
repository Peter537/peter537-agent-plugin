# Google developer-documentation overlay

Use this optional overlay for developer documentation only when the user explicitly requests Google developer documentation style or repository instructions adopt it. Do not activate it merely because the subject is software, the document is in English, or no other style guide is obvious.

## Authority and scope

Project-specific requirements, the user's instruction, factual and semantic fidelity, exact accepted edits, source language, and accessibility or legal constraints remain controlling. Apply only the Google guidance that fits the document's function and repository conventions.

Google describes its guide as a house style rather than an industry standard, and the guide itself puts project-specific guidance first. Do not claim that edited work is Google-approved, Google-authored, certified, or fully conformant. Do not import Google product-specific terminology, branding, or formatting into an unrelated project.

## Operational overlay

- Put useful information, the reader's goal, or the required action before background that can wait.
- Use an approachable, respectful technical voice without becoming chatty, promotional, slang-heavy, or artificially entertaining.
- Name the responsible actor when responsibility matters. Prefer active voice when it clarifies who acts; retain passive voice when the actor is unknown, irrelevant, intentionally de-emphasized, or less important than the affected object.
- Address the reader directly when the reader acts. Write procedural actions as imperative steps, keep one meaningful action per step when practical, and use numbered lists only for real sequences.
- Put a condition before or close to the instruction it governs when doing so prevents the reader from acting before learning the condition.
- Keep terminology and grammatical relationships unambiguous for global readers. Avoid unexplained culture-specific references and do not replace necessary technical distinctions with simpler but inaccurate language.
- Preserve descriptive headings, meaningful link text, semantic structure, non-visual cues, and alternative text requirements. Wording improvements alone do not establish accessibility conformance.
- Use only claims supported by the brief and repository evidence. Preserve uncertainty, modality, prerequisites, limitations, and product boundaries rather than making the prose sound more decisive.

## Function and locale boundaries

Apply these choices through the document-function profiles rather than forcing one tone on every section. Reference material can remain neutral and compact; procedures can be direct; explanations can provide warranted context; warnings and policies retain their required force.

The guide's US English conventions do not authorize translation or locale normalization. Preserve the repository's spelling variant, source language, established terminology, and intentional voice unless the user explicitly requests a change.

## Official sources

- [About this guide](https://developers.google.com/style/) establishes the reference hierarchy and permits departures that improve clarity for the domain and readers.
- [Philosophy of this style guide](https://developers.google.com/style/philosophy) defines the guidance as a house style, not an industry standard or replacement for an adopted guide.
- [Voice and tone](https://developers.google.com/style/tone) covers approachable, respectful, information-focused developer prose.
- [Active voice](https://developers.google.com/style/voice) explains actor clarity and legitimate uses of passive voice.
- [Procedures](https://developers.google.com/style/procedures) covers action-oriented steps, context, results, and procedural organization.
- [Write for a global audience](https://developers.google.com/style/translation) covers stable, unambiguous, localization-aware language.
- [Write accessible documentation](https://developers.google.com/style/accessibility) covers navigable structure, descriptive text, and non-visual access to meaning.
- [Avoid excessive claims](https://developers.google.com/style/excessive-claims) covers evidence-bounded descriptions of products and capabilities.
